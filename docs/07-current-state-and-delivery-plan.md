文档版本：v0.1  |  日期：2026-08-04  |  状态：Delivery Baseline

本文把 2026-08-04 的仓库实现与既有产品、架构、数据、工作台和 Agent 文档交叉比对，回答两个问题：RiskTrace 现在真实完成了什么，以及从 `#003` 开始怎样形成第一条可演示、可验证的业务闭环。

评估基线为提交 `392a9d2`（`#002`）。百分比是用于排序的阶段性判断，不是测试覆盖率、里程碑验收率或工时进度。

## 1. 当前阶段结论

RiskTrace 不是空壳。仓库已经有可阅读、可继续实现的双应用结构、真实依赖就绪检查、核心追溯模型和迁移基线；它也还不能称为 MVP 产品，因为从历史消息进入系统到事件、时间线、工作台和原始证据下钻的链路尚未实现。

更准确的定性是：

> 已完成 production-oriented engineering skeleton，尚未完成 product vertical slice。

阶段性完成度可按以下口径理解：

| 维度 | 估计 | 仓库事实 | 解释 |
| --- | ---: | --- | --- |
| 工程基础设施 | 70% | Next.js、FastAPI、Compose、PostgreSQL、Redis、MinIO、Alembic、检查入口均已落库 | 指工程基线完成度，不代表完整栈已在本次评估中运行验证 |
| 数据模型 | 40% | 已有 `RawDocument`、`Event`、`Entity`、`EventDocument`、`EvidenceLink` | 核心来源与证据关系已存在，观点、计算、快照、告警等对象尚未落库 |
| 业务后端 | 10% | 当前公开路由只有健康检查，业务模块、导入和事件引擎尚未实现 | 数据表存在不等于业务行为存在 |
| 研究工作台 UI | 5% | 首页只展示真实平台状态和系统边界 | 风险总览、事件工作台、时间线和证据抽屉尚未实现 |
| Agent / LLM | 0% | 只有边界文档和 vendored 依赖，没有模型调用路径 | 依赖可用性不计为产品能力 |
| 完整 Demo 闭环 | 0–5% | Web → API → 基础设施状态链已定义，但 Information → Research 链路未形成 | 尚不能演示消息如何转化为研究结果 |

整体约为 20%，只适合作为方向性判断。后续不再以仓库文件数、第三方源码量或基础设施组件数衡量产品完成度，而以端到端验收场景是否成立衡量。

## 2. 已经做对的事情

### 2.1 模块化单体方向正确

当前实际结构与 `01-platform-architecture.md`、`05-repository-structure.md` 一致：

```text
Next.js Web
  → FastAPI 模块化单体
  → PostgreSQL / Redis / MinIO
```

采集、事件、评分、证据、通知和报告继续作为同一后端内部模块演进。没有独立扩缩容或故障隔离证据前，不拆微服务，不引入 Kafka、Kubernetes 或复杂自治多 Agent 编排。

### 2.2 产品主链与权责边界正确

`docs/README.md` 定义的主链不是“新闻 → LLM → 风险分”，而是：

```text
Source Adapters
  → Raw Store
  → Normalization / Dedup / Quality
  → Event Engine
  → LLM Semantic Layer
  → Aggregation & Scoring
  → Transmission Hypothesis
  → Evidence / Rule Validation
  → Alert Engine
  → Research Workspace
  → Human Review
```

`04-agent-rule-boundary.md` 又把职责限定为：规则和代码负责确定性计算与状态；传统模型负责高频模式识别；LLM 只输出语义候选；研究员负责重大结论和外发。这是 RiskTrace 成为研究工具而不是 AI 包装层的关键。

### 2.3 追溯模型先于语义层落地

当前 ORM 和第一份迁移真实包含：

- `RawDocument`
- `Event`
- `Entity`
- `EventDocument`
- `EvidenceLink`

`RawDocument` 已覆盖来源、发布时间、采集时间、作者哈希、原文、互动、采集方式、许可范围、内容哈希和原始载荷引用；`(platform, source_id)` 有唯一约束。这为以下链路提供了数据库基础：

```text
研究结论
  → EvidenceLink
  → RawDocument
  → 原始帖子 / 新闻 / 公告
```

当前只应称为“追溯数据结构已实现”，不能称为“证据下钻已实现”，因为业务查询、接口和页面还不存在。

### 3.1 对原始建议的三处校正

1. **`#003` 与 `#004` 必须分责。** `#003` 用显式历史场景清单把导入数据绑定为一个已知事件，验证数据、API、UI 和证据链；`#004` 再让同一批逐条回放的消息无需预绑定即可自动聚类、计算热度并推动状态机。前者不得宣称已实现自动事件发现。

2. **业务接口不能绕过租户边界。** `05-repository-structure.md` 已规定，在认证落地前不新增返回租户业务数据的公开接口。因此 `#003` 必须同时建立最小、服务端确定的演示身份与租户上下文；无需引入新基础设施，但不能信任请求中的任意 `tenant_id`。

3. **API 优先复用既有契约。** 第一切片使用 `GET /api/events`、`GET /api/events/{id}/workspace` 和 `GET /api/events/{id}/evidence`。若实现时发现必须新增 `GET /api/events/{id}` 或 `/documents`，应先说明它与聚合工作台、证据筛选接口的边界，并同步更新相关设计文档。

## 4. 立即生效的开发策略

从 `#003` 开始冻结横向基础设施扩张：

- 不新增数据库、中间件、消息系统、Agent 框架或大体量第三方源码。
- 已 vendored 的 Celery、Sentence Transformers、Pydantic AI、ECharts、XYFlow 和 pgvector 暂不推翻，但“存在于仓库”不计为已接入。
- 只有当前纵向切片出现可复现阻塞，并证明现有能力无法解决时，才讨论新增依赖。
- LLM 在历史回放、Event、时间线和证据下钻通过验收前保持关闭。
- 历史 fixture 必须有来源说明、采集/整理方式、许可范围和时间语义；不能使用看似真实但无法追溯的假数据。
- 每个提交以可运行的业务结果为边界，避免把迁移、后端、前端拆成长期互不可用的半成品。

第一条要证明的产品链是：

```text
historical_event.jsonl
  → RawDocument schema 校验
  → 幂等导入 / 精确去重
  → 已知历史 Event 与文档关联
  → 事件列表 / 时间线 API
  → Risk Overview
  → Event Workspace
  → Evidence Drawer
```

## 5. `#003`：Historical Replay & Evidence Slice

### 5.1 目标

让一个合规、可追溯的历史事件第一次完整穿过数据库、后端接口和前端页面。这个提交验证“证据闭环和产品形态”，不验证自动事件发现、LLM 语义理解或风险预测。

### 5.2 实现范围

#### 历史场景与数据契约

- 建立一个历史事件 fixture 目录，包含事件清单、`historical_event.jsonl` 和来源/许可说明。
- 初始数据至少覆盖事实、新闻、舆情三类；行情若无法合法、稳定取得，显式标记缺失，不填 0、不伪造曲线。
- 解析并校验现有 `RawDocument` 契约；内部统一 UTC，展示默认 Asia/Shanghai。
- 不合格记录进入可观察的 rejected 结果，包含行号和原因，不静默跳过。

#### 导入与幂等

- 提供一个明确的导入入口和汇总结果：读取数、写入数、重复数、拒绝数。
- `(platform, source_id)` 作为来源级幂等键；`content_hash` 用于发现跨 ID 内容重复，不直接覆盖原始记录。
- 同一 fixture 连续导入两次，第二次不得新增 `RawDocument`、`Event` 或重复关联。
- `#003` 允许由 fixture 的显式场景标识创建一个已知 Event；页面必须标记为“历史回放”。

#### 服务端租户边界

- 建立最小演示认证/身份入口，由服务端产生固定的演示租户上下文。
- 所有事件、工作台和证据查询都使用认证上下文过滤，拒绝用前端传入的 `tenant_id` 直接决定数据范围。
- 这一阶段不要求完整 RBAC 管理后台，但不得暴露无保护的租户业务接口。

#### API 与 UI

- `GET /api/events`：返回历史回放事件列表、来源结构、文档数和更新时间。
- `GET /api/events/{id}/workspace`：第一版只返回事件头部、数据质量和文档数量时间线；未实现字段明确为空或 unavailable。
- `GET /api/events/{id}/evidence`：按来源、平台、时间桶分页读取原始证据。
- Risk Overview：展示真实导入事件，不展示风险分、情绪分或虚构状态。
- Event Workspace：展示事件信息、热度时间线、来源结构和关联实体的已知部分。
- Evidence Drawer：从事件或时间桶打开对应 `RawDocument`，显示来源、发布时间、采集时间、原文/许可状态。

### 5.3 验收门槛

1. 空库导入一次成功，重复导入数据行数和关联数不增长。
2. 一条 schema 错误记录被拒绝并给出稳定错误原因；其余合法记录继续处理或按明确的原子批策略回滚。
3. 浏览器可从事件总览进入工作台，点击时间桶后看到对应原始证据。
4. 页面每个数量都能由数据库查询复核；缺失行情或来源显示为缺失/降级。
5. 跨租户读取测试失败，未认证请求不能访问业务数据。
6. 不存在 LLM 调用、Celery 任务、embedding 或权威风险分数。

## 6. `#004`：Event Engine

### 6.1 目标

把 `#003` 的“已知场景回放”升级为“消息逐条进入后自动形成 Event”，并让热度和状态转换可复算。

### 6.2 实现范围

- 引入可控的 replay clock，按 `published_at` 加速注入同一历史数据。
- 完成文本标准化、精确去重和满足演示需求的近似去重；独立样本数与传播量分离。
- 以确定性规则和轻量传统方法形成事件候选；LLM 最多在后续负责命名，不能参与状态转换。
- 生成版本化时间桶：总量、独立样本数、来源结构、采集延迟和完整性状态。
- 落地最小状态机：`candidate → active → cooling → closed`；其他状态按真实需求逐步启用。
- `#003` 页面改为消费 Event Engine 结果，不保留一套演示专用计算路径。

### 6.3 验收门槛

1. 同一输入、时钟和规则版本得到相同事件、时间桶和状态轨迹。
2. 消息无需 fixture 预写 event ID 即可自动形成目标 Event。
3. 重复/转发洪峰不会被计算成相同数量的独立观点样本。
4. 达到规则阈值后 Event 自动进入 `active` 并出现在总览。
5. 每个时间桶可下钻到输入文档集合；延迟或缺失来源降低完整性，不伪造满置信度。

## 7. `#005`：Opinion Extractor

### 7.1 前置条件

只有 `#004` 的去重、Event、证据 ID 和降级路径通过验收后才开始。实现时以 `04-agent-rule-boundary.md` 中的 `OpinionRecord` 为权威契约，避免另建一套字段近似但不兼容的 schema。

### 7.2 实现范围

- 输入为去重后的单条或小批文本、Event 上下文和允许引用的 document IDs。
- 输出至少包含 `document_id`、`target_entity_id`、`stance`、`emotion`、`reason`、`claim_type`、`evidence_span` 和 `model_confidence`。
- 服务端严格校验 schema、实体 ID、证据 ID 和枚举；无效输出进入 degraded，不写权威字段。
- 用确定性程序聚合观点占比、独立样本数和变化速度；LLM 不负责聚合百分比。
- UI 增加观点簇与反向证据入口，每个观点可下钻到原文。

### 7.3 验收门槛

1. 不存在的 evidence/document ID 被拒绝并记录。
2. 关闭 LLM 后，导入、事件、时间线和证据浏览继续可用并显示语义层降级。
3. 观点百分比由有效独立样本复算，分母和样本数可见。
4. 外部文本中的提示词注入不能修改系统权限或越权调用工具。

## 8. `#006`：Transmission Graph

### 8.1 前置条件

需要已确认 Event、观点簇、实体注册表以及可版本化的产业链/公司知识记录。没有知识来源和证据时，不生成看似完整的传导图。

### 8.2 实现范围

- 使用既有节点类型：Event / Mechanism / Industry / Company / MarketVariable。
- LLM 只提出 `TransmissionEdgeCandidate`；边必须引用 evidence IDs 和 knowledge IDs。
- 规则层校验实体、方向、重复边、来源覆盖和置信度；所有边默认标记为候选。
- 工作台显示高置信度主干和低置信度候选，明确区分事实、假设与人工确认。
- 点击任一边打开证据与知识依据；不把时间相关性自动描述为因果关系。

### 8.3 验收门槛

1. 至少形成一条可解释的 Event → Mechanism → Industry → Company 候选链。
2. 每条边均能下钻到有效证据和知识记录；无引用边被拒绝。
3. 相同分析版本可重现相同输入集合；模型版本和提示词版本有记录。
4. 研究员的确认/拒绝先进入版本化决策记录，不覆盖原候选。

## 9. `#007` 以后：完成 MVP 闭环

在前三个业务切片稳定后，再按既有总开发文档推进：

| 提交主题 | 主要结果 | 关键门槛 |
| --- | --- | --- |
| `#007` 确定性评分与告警 | 热度、来源质量、事实支持、暴露等因子形成版本化 risk score；触发站内告警 | 结果可由 `calculation_id` 复算；LLM 不直接给分 |
| `#008` 人工审核与快照 | 观点/传导审核、研究备注、analysis version、snapshot | 修改保留前后值与操作者；旧快照可复现 |
| `#009` 简报与导出 | 基于冻结 snapshot 生成风险卡片和 CSV/JSON/HTML 中至少一种 | 所有数字来自冻结字段，事实句有 evidence ID |
| `#010` MVP 演示加固 | 至少 10 个历史回放事件、完整 RBAC、一个外部通知渠道、性能与故障演练 | 满足 `01-platform-architecture.md` 与 `docs/README.md` 的端到端验收场景 |

编号表示推荐的可审查交付顺序，不要求机械地一项只对应一个 Git 提交；若某项过大，应继续拆分，但每个合并点必须保持可运行。

## 10. 每个后续切片的统一完成定义

一个切片只有同时满足以下条件才算完成：

1. **文档已定义**：输入、输出、权限、降级和非目标明确。
2. **代码已实现**：真实调用路径使用该能力，不是孤立脚本或未接线组件。
3. **测试已验证**：至少覆盖正常路径、幂等/复算、失败降级和越权边界。
4. **运行已验证**：从实际入口触发，检查 API、数据库结果、页面和静态资源；不能只以 health endpoint 代替。
5. **证据可下钻**：页面结论、时间桶、观点或传导边能回到 `evidence_id` 或 `calculation_id`。
6. **缺失不伪造**：未接入来源、行情、模型或权限能力显示 unavailable/degraded，不用假数据补齐。

## 11. 当前剩余风险

- 完整 Compose 和 vendored 依赖的构建状态具有环境依赖，执行每个切片前仍需现场预检，不能沿用旧结论。
- 当前 `RawDocument.tenant_id` 可空，而其他业务对象多数不可空；导入设计必须明确共享原始数据与租户数据的边界，不能临时用空值绕过隔离。
- `(platform, source_id)` 是全局唯一约束，是否允许同一原始文档被多个租户引用需要在 `#003` 实现前写清，不应在 importer 中暗自决定。
- 现有 Event 状态枚举多于 `#004` 首版状态机；未启用状态必须保持不可达或有明确转换规则。
- 当前第三方源码显著放大仓库体积和依赖面；在形成产品闭环前继续 vendoring 会增加维护、许可证和供应链审查成本，却不会提高演示完成度。

## 12. 下一步唯一优先事项

下一次业务开发从 `#003 Historical Replay & Evidence Slice` 开始。完成之前不接 LLM、不新增基础设施、不开发传导图，也不以静态 mock 页面替代真实导入与证据查询。

当评委能看到一个历史事件逐步出现、点击时间桶查看真实来源文档，并理解“这些数量从哪里来”时，RiskTrace 才第一次从工程仓库变成可解释的产品。
