可以。把它整合成一个完整的“数据导入—事件归类—入库管理—确定性评分—后验校准”管线，数学上每一步都有可解释的评分函数，工程上每一步都有明确的服务、状态和数据库对象。核心不是“抓新闻然后算热度”，而是：

[
\boxed{
\text{Raw Feed}
\rightarrow
\text{Rule 1: Classification}
\rightarrow
\text{Rule 2: Admission Decision}
\rightarrow
\text{Event}
\rightarrow
\text{Rule 3: Deterministic Scoring}
\rightarrow
\text{Rule 4: Posterior Calibration}
\rightarrow
\text{Snapshot}
}
]

其中必须严格区分四类结果：

[
\boxed{
D=\text{Admission Decision},
\qquad
S=\text{Raw Score},
\qquad
\tilde S=\text{Calibrated Score},
\qquad
C=\text{Confidence}
}
]

分别回答：

* (D)：这条信息是 DROP、WAIT、ADMIT 还是 ATTACH？
* (S)：正式 Event 在当前可观测数据下的基础风险/事件评分是多少？
* (\tilde S)：后验校准后的稳定评分是多少？
* (C)：当前证据条件下这个评分有多稳定？

这些结果绝对不能混成一个分数。Rule 2 是入库管理，不再输出给用户展示的 `Admission Score`；Rule 3/4 才负责评分。

建议实际管线做成：

```text

                ▼

                │
                ▼
         ② Preprocessor
       清洗 / 去广告 / 去垃圾
                │
                ▼
         ③ Rule 1 Event Classification
       事件归类 / 旧事件匹配
                │
                ▼
         ④ Rule 2 Admission Management
             入库管理
          ┌─────┼─────┐
          ▼     ▼     ▼
        DROP   WAIT  ATTACH
                │
                ▼
              ADMIT
                      │
                      ▼
         ⑤ Event Clustering
              在线事件聚类
                      │
                      ▼
```

# 二、第一层：什么信息有资格进入候选池

所有抓取数据可以进入原始表：

```text
raw_messages
```

但不能全部进入 `events`。

首先做廉价过滤。

定义原始消息：

[
x=(t,s,a,c,m)
]

其中：

* (t)：timestamp；
* (s)：source；
* (a)：author；
* (c)：content；
* (m)：engagement metadata。

工程上：

```text
raw_messages
├── id
├── source
├── source_msg_id
├── author_id
├── content
├── published_at
├── likes
├── comments
├── reposts
├── views
└── raw_json
```

第一层不调用大模型，使用规则处理：

```text
广告
纯链接
博彩
招聘
重复采集
过短文本
无意义文本
明显机器人模板
```

直接过滤。

这一步目标不是判断“重要不重要”，只是去垃圾。

# 三、第二层：判断“它是不是事件”

这是第一个真正有意义的数学条件。

金融事件本质上应该包含一个状态变化：

[
(S,P,V_0)\rightarrow(S,P,V_1)
]

其中：

* (S)：Subject；
* (P)：Property；
* (V_0,V_1)：变化前后状态。

例如：

[
(\text{宁德时代},\text{production},
\text{normal})
\rightarrow
(\text{宁德时代},\text{production},
\text{suspended})
]

这就是事件。

而：

> 宁德时代是全球动力电池龙头。

不存在状态变化：

[
\Delta V=0
]

因此不是 Event。

工程上让 Event Extractor 输出：

```json
{
  "is_event": true,
  "subject": ["宁德时代"],
  "event_type": "production_disruption",
  "state_change": {
    "property": "production_status",
    "from": "normal",
    "to": "suspended"
  },
  "time": "...",
  "location": "Hungary"
}
```

这里 LLM 的作用非常明确：

> LLM 负责把自然语言变成结构化 Event Claim。

它不负责最后决定是否创建 Event。

# 四、第三层：市场相关性

有事件，不代表是金融事件。

定义：

[
M(x)\in[0,1]
]

表示：

[
M(x)=P(\text{该事件能够影响研究资产}\mid x)
]

进一步要求找到至少一条映射：

[
\text{Event}
\rightarrow
\text{Factor}
\rightarrow
\text{Asset}
]

例如：

[
\text{宁德时代工厂停产}
\rightarrow
\text{产能下降}
\rightarrow
\text{CATL earnings}
]

或者：

[
\text{Apple更换OLED供应商}
\rightarrow
\text{供应链订单变化}
\rightarrow
\text{京东方}
]

工程上保存：

```json
{
  "market_relevance": 0.91,
  "related_assets": [
    {
      "symbol": "300750.SZ",
      "relation": "direct"
    }
  ],
  "impact_channels": [
    "supply",
    "earnings"
  ]
}
```

如果：

[
M(x)<\theta_M
]

例如：

[
\theta_M=0.5
]

直接 Drop。

# 五、第四层：潜在影响评分

即使与市场相关，也不一定值得进入系统。

例如：

> 某上市公司举办员工运动会。

确实与上市公司有关，但：

[
I(x)\approx0
]

所以定义 Potential Impact：

[
I(x)
====

\sum_{k=1}^{K}
w_k I_k(x)
]

影响通道至少可以定义：

[
\mathcal C=
{
\text{earnings},
\text{supply},
\text{demand},
\text{regulation},
\text{liquidity},
\text{governance},
\text{reputation},
\text{macro},
\text{expectation}
}
]

例如：

```text
工厂停产
    ↓
Supply = 0.9
Earnings = 0.7
Expectation = 0.8
```

得到：

[
I=0.84
]

工程上不要让 LLM直接输出一句“重要”。

要求它解释：

```json
{
  "impact_score": 0.84,
  "channels": [
    {
      "type": "supply",
      "score": 0.92,
      "reason": "production capacity disruption"
    },
    {
      "type": "earnings",
      "score": 0.71
    }
  ]
}
```

这样后面 Transmission Graph 可以直接复用。

# 六、第五层：Novelty——是不是一个新事件

这是事件准入的关键。

设当前事件库：

[
E={e_1,e_2,\dots,e_n}
]

对新消息 (x)，首先检索过去一定窗口内的候选事件，例如：

[
\Delta t\le48h
]

然后计算：

[
S(x,e)
======

\alpha S_{\text{sem}}
+
\beta S_{\text{entity}}
+
\gamma S_{\text{time}}
+
\delta S_{\text{type}}
]

建议第一版：

[
\boxed{
S(x,e)=
0.55S_{\text{sem}}
+0.20S_{\text{entity}}
+0.15S_{\text{time}}
+0.10S_{\text{type}}
}
]

语义相似度：

[
S_{\text{sem}}
==============

\frac{v_x^\top v_e}
{|v_x||v_e|}
]

实体相似度：

[
S_{\text{entity}}
=================

\frac{|E_x\cap E_e|}
{|E_x\cup E_e|}
]

时间衰减：

[
S_{\text{time}}
===============

e^{-|\Delta t|/\tau}
]

例如：

[
\tau=6h
]

事件类型：

[
S_{\text{type}}
===============

\begin{cases}
1,&T_x=T_e\
0,&T_x\neq T_e
\end{cases}
]

工程流程：

```text
Candidate
   ↓
Vector Search
找最近 Top-K Event
   ↓
计算完整 Event Similarity
   ↓
max similarity
```

例如：

[
\max_e S(x,e)=0.91
]

超过：

[
\theta_{\text{attach}}=0.78
]

则：

```text
ATTACH
```

不是新事件。

# 七、Rule 2 入库管理

只有没有匹配到旧事件时，才讨论“要不要创建新事件”。这里不再定义面向用户的 `Admission Score`，而是定义 Rule 2 的内部入库裁决因子，用来支持 DROP / WAIT / ADMIT / ATTACH。

定义：

[
A_{\text{rule2}}(x)
====

w_MM+
w_CC+
w_II+
w_NN+
w_QQ
]

其中：

* (M)：Market Relevance；
* (C)：State Change；
* (I)：Potential Impact；
* (N)：Novelty；
* (Q)：Source Quality。

建议：

[
\boxed{
A=
0.20M+
0.20C+
0.30I+
0.20N+
0.10Q
}
]

影响分数 (I) 权重最高。

但不要简单：

[
A_{\text{rule2}}>0.7\Rightarrow ADMIT
]

最好加硬约束：

[
M>\theta_M,\qquad
C>\theta_C,\qquad
I>\theta_I
]

之后才看 (A)。

工程判断：

```text
if market_relevance < 0.5:
    DROP

elif eventness < 0.6:
    DROP

elif matched_existing_event:
    ATTACH

elif potential_impact < 0.4:
    DROP

elif admission_decision_score >= 0.75:
    ADMIT

else:
    WAIT
```

因此最终有四种命运：

```text
DROP
WAIT
ATTACH
ADMIT
```

这比简单 true / false 健壮得多。

# 八、为什么必须存在 Candidate Event

因为金融风险最有价值的信息往往初期不可信。

例如匿名帖：

> 某银行可能存在流动性问题。

它可能：

[
Q=0.15
]

但：

[
I=0.95
]

你不能因为来源低质量直接删除。

所以：

[
I\gg0,\quad Q\ll1
]

进入：

```text
Candidate Event
```

而不是 Drop。

Candidate 的升级条件可以定义：

[
C_t=
\lambda_1D_t+
\lambda_2Q_t+
\lambda_3V_t
]

其中：

* (D_t)：独立来源数量；
* (Q_t)：最高来源可信度；
* (V_t)：传播速度。

如果：

[
C_t>\theta_C
]

则：

```text
Candidate → Confirmed
```

例如：

```text
17:01 匿名雪球爆料
       ↓
Candidate

17:08 第二个独立用户确认
       ↓

17:14 财联社报道
       ↓
Confirmed Event
```

这就是事件回放中非常漂亮的一条时间线。

# 九、Event 创建之后，聚类才真正开始

Event 不应该只是 title。

应该维护一个聚类中心：

[
c_e=
\frac{\sum_i w_i v_i}
{\sum_iw_i}
]

而不是简单平均。

权重 (w_i) 可以基于：

[
w_i=f(\text{source quality},\text{originality})
]

例如原创 Reuters 权重大，机器人转载权重小。

新 evidence 加入：

[
c'_e
====

\frac{W_ec_e+w_xv_x}
{W_e+w_x}
]

其中：

[
W_e=\sum_iw_i
]

这样事件的语义中心会实时更新。

工程表：

```text
events
├── id
├── canonical_title
├── summary
├── event_type
├── status
├── centroid_embedding
├── first_seen_at
├── last_seen_at
├── admission_score
├── confidence
├── heat_score
├── momentum
├── risk_score
└── evidence_count
```

关系表：

```text
event_evidences
├── event_id
├── message_id
├── similarity
├── source_weight
├── novelty
└── attached_at
```

# 十、去重和事件聚类必须分开

还有一层经常被忽略：

[
\text{Duplicate}\neq\text{Same Event}
]

例如：

A：

> 财联社：宁德时代匈牙利工厂暂停生产。

B：

> 据财联社消息，宁德时代匈牙利工厂暂停生产。

基本是同一条信息：

[
S_{\text{duplicate}}>0.95
]

属于 Duplicate。

但是：

C：

> 宁德时代回应称工厂仅进行设备维护。

这是同一个 Event，但绝不是 duplicate。

所以工程必须是：

```text
Message
 ↓
Near Duplicate Detection
 ↓
Evidence Unit
 ↓
Event Matching
 ↓
Event
```

Duplicate 可以用：

```text
SimHash
MinHash
embedding cosine
URL canonicalization
```

完成。

LLM 不应该参与。

# 十一、热度 Heat 只对 Event 计算

事件正式存在后，才计算：

[
H_t
]

我建议定义：

[
\boxed{
H_t=
0.20V_t+
0.25G_t+
0.15E_t+
0.15D_t+
0.15A_t+
0.10C_t
}
]

分别为：

[
V=\text{Volume}
]

[
G=\text{Growth}
]

[
E=\text{Engagement}
]

[
D=\text{Source Diversity}
]

[
A=\text{Authority}
]

[
C=\text{Cross-platform Coverage}
]

这里 Growth 权重最高，因为金融系统更应该捕捉“突然升温”。

# 十二、Volume 不用原始数量

否则头部热点永远霸榜。

定义：

[
V_t=
\operatorname{norm}
\left(
\log(1+N_t)
\right)
]

例如：

[
10\rightarrow100
]

和：

[
10000\rightarrow10100
]

原始增长都可能看起来大，但前一个实际更值得警觉。

工程层每个 Event 可以维护滑动窗口：

```text
5 min
10 min
30 min
1 h
6 h
24 h
```

---

# 十三、Growth 用异常度而不是简单环比

不要只算：

[
\frac{N_t-N_{t-1}}{N_{t-1}}
]

因为：

[
1\rightarrow5
]

就会得到 400%。

建议建立 baseline：

[
Z_t=
\frac{N_t-\mu_t}
{\sigma_t+\varepsilon}
]

其中：

[
\mu_t=E[N_t]
]

[
\sigma_t=\sqrt{\operatorname{Var}(N_t)}
]

然后：

[
G_t=
\sigma(kZ_t)
]

其中 sigmoid：

[
\sigma(x)=\frac1{1+e^{-x}}
]

工程上 `EventMetricWorker` 每 5 分钟计算一次：

```text
event_metrics
├── event_id
├── timestamp
├── msg_count_5m
├── msg_count_1h
├── volume
├── growth
├── engagement
├── diversity
├── authority
├── coverage
├── heat
├── momentum
└── risk
```

# 十四、来源 Diversity 用信息熵

设来自 (K) 个来源：

[
p_i=
\frac{N_i}{\sum_jN_j}
]

则：

[
D=
-\sum_{i=1}^Kp_i\log p_i
]

再归一化：

[
D^*=
\frac{D}{\log K}
]

于是：

[
D^*\in[0,1]
]

如果 1000 条全部来自微博：

[
D^*\approx0
]

如果：

```text
微博
雪球
财联社
Reuters
微信公众号
交易所
```

都有独立传播：

[
D^*\rightarrow1
]

工程优势是很明显的：这个指标完全确定、可解释，不需要 LLM。

---

# 十五、互动量 Engagement 必须平台内标准化

微博 1000 个赞和雪球 1000 个赞不是一个概念。

因此：

[
E_i
===

F_{P_i}(e_i)
]

这里 (F_{P_i}) 是平台 (P_i) 的经验分布函数。

换句话说：

> 这个互动量位于本平台所有内容的什么百分位。

例如：

```text
微博 5000 likes
= 98th percentile
```

则：

[
E=0.98
]

工程上每天离线更新：

```text
platform_baseline
```

而不是硬编码：

```text
500 likes = high
```

# 十六、Momentum 应该单独展示

定义：

[
M_t=
H_t-H_{t-\Delta t}
]

例如：

[
H_t=82
]

存在两种完全不同状态：

[
M_t=+18
]

表示正在爆发。

以及：

[
M_t=-21
]

表示热度正在退潮。

工程 UI 最好直接显示：

```text
Heat      82
Momentum +18 ↑↑
```

不要把两者揉成一个数字。

# 十七、Risk Score 与 Heat 必须独立

最重要的一点：

[
\boxed{
\text{Hot}\neq\text{Risky}
}
]

例如：

> 某公司新品发布。

可能：

[
H=95
]

但是：

[
R=20
]

另一件事：

> 某银行出现小范围流动性传言。

可能：

[
H=30
]

但：

[
R=90
]

Risk 可以定义为：

[
R=
\alpha X_{\text{event}}+
\beta X_{\text{source}}+
\gamma X_{\text{diffusion}}+
\delta X_{\text{market}}+
\eta X_{\text{completeness}}
]

其中：

* (X_{\text{event}})：事件状态、潜在影响、事实支持等事件自身可观测量；
* (X_{\text{source}})：来源质量、独立来源数、来源类型结构；
* (X_{\text{diffusion}})：热度、动量、传播覆盖和异常速度；
* (X_{\text{market}})：行情反应、行业/实体相关性和市场暴露；
* (X_{\text{completeness}})：数据完整度、来源降级和采集延迟。

Rule 3 不能依赖 Agent 2 生成的观点归因、情绪解释或传导假设。Agent 2 可以在 Snapshot 中解释这些评分因子，但不能把解释反写为权威评分输入。

例如：

[
\boxed{
R=
0.35I+
0.20S+
0.30X+
0.15U
}
]

这里 Exposure 指：

[
X=
\text{事件影响资产的重要程度}
]

后面可以直接接 Transmission Graph。

# 十八、整个系统真正的数据状态机

工程上建议不要只保存一堆 score，而要显式做状态机：

```text
RAW
 ↓
FILTERED
 ↓
EXTRACTED
 ↓
      ┌──────────── DROP
      │
ADMISSION
      │
      ├──────────── ATTACHED
      │
      ├──────────── CANDIDATE
      │                  │
      │             evidence ↑
      │                  │
      └──────────── CONFIRMED
                         │
                    MONITORING
                         │
                       COOLING
                         │
                       CLOSED
```

也就是说 Event 本身还有生命周期：

[
\text{Candidate}
\rightarrow
\text{Confirmed}
\rightarrow
\text{Active}
\rightarrow
\text{Cooling}
\rightarrow
\text{Closed}
]

例如定义：

[
M_t<0
]

持续 6 小时，并且：

[
H_t<\theta_H
]

则：

```text
Active → Cooling
```

持续 24h：

```text
Cooling → Closed
```

如果之后重新爆发：

```text
Closed → Reactivated
```

而不是重新创建一个 Event。

# 十九、Agent 和规则的边界

最终架构一定要这样划：

```text
                 Algorithm
                    │
      ┌─────────────┼─────────────┬─────────────┐
      ▼             ▼             ▼             ▼
    Dedup      Classification  Admission      Scoring
                 Rule 1        Rule 2        Rule 3
                                               │
                                               ▼
                                      Posterior Calibration
                                             Rule 4

-----------------------------------------------------------

                    Agent
                     │
        ┌────────────┼─────────────┐
        ▼            ▼             ▼
   Event Tags   Opinion Attribution Report Rendering
   Agent 1      Transmission Analysis  Agent 2
```

数学上：

规则链先生成：

[
S_t=g(X_{\text{event}},X_{\text{source}},X_{\text{diffusion}},X_{\text{market}})
]

[
\mathcal C(S_t,E_t,D_t)\rightarrow(\tilde S_t,C_t,[L_t,U_t])
]

其中 \(S_t\) 是 Rule 3 基础分，\(\tilde S_t\) 是 Rule 4 后验校准分。

Agent 之后生成：

[
Y=f_{\theta}(\text{Event}, \tilde S_t, C_t, [L_t,U_t], \text{Evidence})
]

其中 \(Y\) 是事件标签、观点归因、传导假设、评分解释和报告文本。

[
\boxed{\text{Agent 不参与基础分数和后验校准分数形成}}
]

所以：

> **规则算法负责归类、入库、评分和后验校准；Agent 负责标签、解释、归因、传导假设和报告。**

这个边界非常适合向评委解释。
