对，重新对齐仓库以后，“确定性评分”在 RiskTrace 里的正确语义应该是：

[
\boxed{
\text{Certainty}(e,t)
=====================

\text{当前证据集合对事件核心事实成立的支持强度}
}
]

它不是“这篇新闻靠不靠谱”，也不是 Admission Score，更不是 Heat / Momentum / Risk。它最直接的职责是驱动：

[
\boxed{\text{candidate}\rightarrow\text{confirmed}}
]

当前代码也正是这么用的：`LifecyclePolicy.advance()` 只在 `candidate` 状态读取 `confirmation_score`，达到 (0.70) 后进入 `confirmed`。

而 `docs/02` 已经明确把数据分成事实源、专业新闻源、舆情源、行情源，其中“事实源负责确认实际发生了什么”，且具有最高事实权重。 所以这里应该做的是一个“证据确认算法”。

## 现有 `confirmation-v1` 应该改

现在代码是：

[
C_{\text{v1}}
=============

0.40D+0.35Q+0.25V
]

其中

[
D=\min\left(\frac{n_{\text{independent}}}{3},1\right)
]

(Q) 是最高来源质量，(V) 是传播速度。

最大的问题是：

[
\boxed{\text{传播速度不能证明事实成立}}
]

传播速度已经属于 Heat / Momentum。文档也明确要求事件计算层分别处理聚类、热度、状态机，而来源质量和事实支持属于确定性聚合。

比如现在：

[
n=3,\qquad Q=0.3,\qquad V=1
]

三个低质量独立社交账号同时疯传谣言：

[
C_{\text{v1}}
=============

# 0.4+0.105+0.25

0.755
]

于是：

[
\text{candidate}\rightarrow\text{confirmed}
]

反过来，一条正式交易所公告：

[
n=1,\qquad Q=1,\qquad V=0
]

只有：

[
C_{\text{v1}}
=============

0.4/3+0.35
\approx0.483
]

这跟 RiskTrace 的数据源设计完全反着来。

---

# 我建议改成 `confirmation-v2`

首先对 Event (e) 当前所有 Evidence：

[
\mathcal D_e(t)={d_1,\dots,d_n}
]

先做现有的精确去重、SimHash 近似去重、转发链识别。

这一步非常关键。

例如：

```text
新华社
 ├─ 微博 A 转发
 ├─ 雪球 B 转发
 └─ 公众号 C 转述
```

不是四个独立来源，而是：

[
n_{\mathrm{independent}}=1
]

因为 `docs/02` 本身已经规定“同组只保留代表文本，传播量单独统计”，不能把传播量再算作独立事实证据。

对每个独立证据根 (d_i)，定义：

[
u_i
===

r_i d_i
]

其中：

[
r_i=\text{source_reliability}_i
]

[
d_i=\text{document_confidence}_i
]

这两个概念仓库文档已经定义过。

注意，我这里刻意不使用 engagement。

点赞、转发、浏览量：

[
\boxed{\text{只进入 Heat，不进入 Certainty}}
]

否则又会回到“越多人传越真”的问题。

---

## 一、分别聚合三类事实证据

将独立 Evidence 分成：

[
\mathcal F=\text{fact sources}
]

[
\mathcal N=\text{professional news}
]

[
\mathcal S=\text{social sources}
]

不要简单相加，使用饱和式的 evidence accumulation：

[
\boxed{
F
=

1-\prod_{i\in\mathcal F}(1-u_i)
}
]

[
\boxed{
N
=

1-\prod_{i\in\mathcal N}(1-u_i)
}
]

[
\boxed{
S
=

1-\prod_{i\in\mathcal S}(1-u_i)
}
]

这个形式很适合 RiskTrace。

比如两个独立专业新闻源都是：

[
u_1=u_2=0.9
]

则：

[
N=1-(1-0.9)^2=0.99
]

但是新增第十个、第十一个新闻不会线性把分数无限往上推。

---

# 二、不同来源类别不能等价

这是整个算法最核心的一步。

定义基础证据支持：

[
\boxed{
E
=

1-(1-F)(1-0.75N)(1-0.35S)
}
]

这里表达的是：

[
\text{Fact}>\text{News}>\text{Social}
]

而不是简单人为加几个权重以后做平均。

这个公式有几个非常好的性质。

如果只有社交媒体，不管多少独立用户：

[
S\rightarrow1
]

也只有：

[
E\rightarrow0.35
]

所以：

[
\boxed{\text{纯社交传播无法把事件“传成事实”}}
]

非常符合 RiskTrace。

如果只有一个可信专业新闻：

[
N=0.9
]

则：

[
E=0.675
]

还没有到确认阈值。

但两个独立专业新闻：

[
N=0.99
]

得到：

[
E=0.7425
]

已经基本满足媒体交叉确认。

而如果一条官方公告：

[
F=0.95
]

直接：

[
E=0.95
]

这才符合“事实源负责确认发生了什么”的产品定义。

---

# 三、再考虑 Cluster Coherence

Certainty 还要防一个问题：

> 聚类错了。

比如一个 Event 里面混进了：

```text
宁德时代欧洲工厂停产
宁德时代欧洲工厂扩产
宁德时代欧洲工厂裁员
```

虽然主体相同，但不是同一个事实。

而现有引擎已经计算：

[
S(x,e)
======

0.55S_{\rm sem}
+0.20S_{\rm entity}
+0.15S_{\rm time}
+0.10S_{\rm type}
]

并保存 `event_documents.similarity`。自动事件设计文档已经规定了这套复合匹配。

所以可以直接定义：

[
G
=

\frac{
\sum_i u_iS(d_i,e)
}{
\sum_i u_i
}
]

这里：

[
G\in[0,1]
]

代表这个证据簇本身有多一致。

但它不能占太大权重，因为：

> “都在说同一件事”和“这件事是真的”是两回事。

因此只作为修正因子：

[
0.85+0.15G
]

---

# 四、必须加入反证

之后 LLM Event Interpreter 已经设计成区分：

```text
factual_claims
uncertain_claims
```

而工作台也要求显示“事实状态”和反向证据。

所以确定性计算最终应该有一个 contradiction factor：

[
X\in[0,1]
]

其中：

[
X=0
]

表示没有发现有效反证，

[
X\rightarrow1
]

表示存在高可信度直接否认。

同样可以采用：

[
X
=

1-\prod_{j\in\mathcal X}
(1-\rho_j u_j)
]

其中 (\rho_j) 是矛盾强度。

例如：

```text
“裁员 10%”
vs
“裁员 12%”
```

属于部分冲突：

[
\rho\approx0.2
]

而：

```text
“董事长已经辞职”
vs
“公司公告：董事长未辞职”
```

属于：

[
\rho=1
]

---

# 最终 Certainty

因此我建议第一版真正使用：

[
\boxed{
C(e,t)
======

E(e,t)
\left(
0.85+0.15G(e,t)
\right)
\left(
1-X(e,t)
\right)
}
]

即：

[
\boxed{
C=
\underbrace{
\left[
1-(1-F)(1-0.75N)(1-0.35S)
\right]
}*{\text{证据支持}}
\cdot
\underbrace{
(0.85+0.15G)
}*{\text{聚类一致性}}
\cdot
\underbrace{
(1-X)
}_{\text{反证惩罚}}
}
]

仍然：

[
C\in[0,1]
]

生命周期继续保持现在代码中的：

[
C\ge0.70
\quad\Rightarrow\quad
\text{candidate}\rightarrow\text{confirmed}
]

即可，不需要改 `LifecyclePolicy`。

## 这几个典型场景就会变得很合理

| Evidence     | Certainty 大致结果 | 状态                   |
| ------------ | -------------: | -------------------- |
| 1 个匿名雪球爆料    |        0.1–0.2 | Candidate            |
| 5 个独立社交账号爆料  |          约 0.3 | Candidate            |
| 1 个高质量财经媒体报道 |         约 0.65 | Candidate            |
| 2 个独立权威媒体确认  |    约 0.72–0.78 | Confirmed            |
| 交易所/公司正式公告   |    约 0.88–0.97 | Confirmed            |
| 社交疯传但官方明确否认  |             很低 | Candidate / Disputed |

这样才会出现 RiskTrace 真正有价值的状态：

[
\boxed{
Heat=0.94,\qquad
Certainty=0.22,\qquad
Risk=0.81
}
]

意思就是：

> **一个传播极快、潜在影响极大，但尚未得到可靠证实的风险事件。**

这比我上一条回答里泛化的“新闻可信度评分”贴近项目本身得多。

还有两个仓库层面的调整我认为应该一起做。第一，删除 `ConfirmationPolicy.velocity_weight`，传播速度只留在 `Heat/Momentum`；第二，当前只有 `events.confidence` 最终值，没有专门保存这次 confirmation 的各因子，而文档要求确定性计算必须可复算、带 `calculation_id/scoring_version/input_document_ids`。 所以最好新增 `event_confirmation_records`，保存 (F,N,S,G,X,C)、输入 Evidence 和 `confirmation-v2` 版本。

另外我核查时发现一个文档不一致：`docs/README.md` 里的生命周期还是 `candidate → active`，但 `自动事件聚类热点计算设计` 和实际 `event-lifecycle-v1` 已经是 `candidate → confirmed → active`。  这个也应该顺手修掉。
