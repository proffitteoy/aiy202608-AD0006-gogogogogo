我筛完后，RiskTrace 不需要找一个“大而全母项目”。比较合适的是下面这套组合，而且我建议直接据此调整当前技术方案。

### 1. 最重要的一个：FastAPI 官方 Full Stack Template

[fastapi/full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template?utm_source=chatgpt.com)

这是我现在最建议直接拿来当 RiskTrace 工程底座的。

它现在已经包括：

`FastAPI + SQLModel + PostgreSQL + React + TypeScript + Vite + Tailwind + shadcn/ui + Docker Compose + JWT + Playwright`

而且是 FastAPI 官方维护的模板，MIT License，目前仍持续更新。([GitHub][1])

这让我改变一个之前的判断：

> **RiskTrace 没必要坚持 Next.js。**

RiskTrace 是研究工作台，不依赖 SEO，也基本不需要 SSR。React + Vite 反而更简单。

因此我现在更倾向：

```text
RiskTrace
├── frontend
│   └── React + Vite + TypeScript + shadcn/ui
│
├── backend
│   └── FastAPI + SQLModel
│
├── PostgreSQL
├── Redis
└── Docker Compose
```

而不是硬凑：

```text
Next.js
   ↓
FastAPI
   ↓
PostgreSQL
```

这样可以直接吃掉官方模板大量成熟代码。

如果你非常想保留 Next.js，则有 `nextjs/saas-starter`，它已经带 Next.js、Postgres、RBAC、shadcn/ui、认证和 activity log。([GitHub][2])

[nextjs/saas-starter](https://github.com/nextjs/saas-starter?utm_source=chatgpt.com)

但我目前反而**不推荐它作为 RiskTrace 主骨架**，因为它本身又带 Drizzle/Postgres 业务层，会和 FastAPI 的 SQLModel 形成两个数据访问体系。

### 2. pgvector

[pgvector/pgvector](https://github.com/pgvector/pgvector?utm_source=chatgpt.com)

这个基本可以确定用。

RiskTrace 有大量：

```text
新闻 A ≈ 新闻 B？
帖子 A ≈ 帖子 B？

      ↓

duplicate
near duplicate
same opinion
same event
```

这些都天然需要 embedding 相似度。

没必要 MVP 就上 Milvus/Qdrant/Weaviate。

直接：

```text
PostgreSQL
├── RawDocument
├── Event
├── Opinion
├── Evidence
└── embedding VECTOR(...)
```

pgvector 支持 cosine、inner product、L2、HNSW、IVFFlat 等，而且和 SQLAlchemy/SQLModel 有现成 Python 集成。([GitHub][3])

也就是说：

> **一个 PostgreSQL 同时负责业务关系数据 + embedding。**

这特别适合 RiskTrace MVP。

Milvus 我看了，能力很强，但它主要面向大规模独立向量检索集群；现在引入属于明显过度设计。([GitHub][4])

---

### 3. sentence-transformers

[Sentence Transformers](https://github.com/huggingface/sentence-transformers?utm_source=chatgpt.com)

用于：

```text
RawDocument
    ↓
embedding
    ↓
相似度
    ↓
去重 / 聚类 / Event formation
```

第一版完全可以：

```text
SentenceTransformer
       ↓
pgvector
       ↓
cosine similarity
       ↓
cluster
```

以后数据量大，再换 Hugging Face 的 Text Embeddings Inference 服务。TEI 本身已经提供 Docker、REST API、GPU inference、reranker 等。([GitHub][5])

但 MVP **不要部署 TEI**，直接 Python library inference。

### 4. Pydantic AI

这个是我认为非常适合 RiskTrace 的项目。

[pydantic/pydantic-ai](https://github.com/pydantic/pydantic-ai?utm_source=chatgpt.com)

相比一上来 LangGraph，我更建议 Pydantic AI。

原因就是 RiskTrace 已经规定：

```text
LLM
不能随便输出自然语言
        ↓
必须输出严格 Schema
        ↓
验证 evidence_id
验证 entity_id
验证 enum
验证 confidence
```

而 Pydantic AI 本身就是 Pydantic 团队做的 type-safe agent framework，支持多个模型提供商。([GitHub][6])

例如未来的：

```python
class OpinionRecord:
    stance: ...
    target_entity_id: ...
    sentiment: ...
    reason: ...
    evidence_ids: ...
```

特别适合直接让 Agent 输出这种模型。

所以：

```text
OpinionExtractorAgent
TransmissionAgent
BriefAgent
```

我建议全部围绕 Pydantic AI 建。

### LangGraph 呢？

我也看了：

[langchain-ai/langgraph](https://github.com/langchain-ai/langgraph?utm_source=chatgpt.com)

它很强，尤其 durable execution、stateful workflow、human-in-the-loop。([GitHub][7])

但 RiskTrace MVP 当前没有真正需要复杂 Agent graph。

所以我的结论是：

> Pydantic AI：现在用。
>
> LangGraph：以后流程复杂再引入。

不要两个一起上。

### 5. Langfuse

[langfuse/langfuse](https://github.com/langfuse/langfuse?utm_source=chatgpt.com)

这个和 RiskTrace 的设计文档高度吻合。

你现在设计里明确要求保存：

```text
model_version
prompt_version
input
output
latency
cost
```

Langfuse 原生就是干这个的，包括：

* LLM traces
* prompt management
* evaluation
* datasets
* cost/metrics
* self-host

而且主体是 MIT license，可以 Docker self-host。([GitHub][8])

所以最终：

```text
RiskTrace
    ↓
Pydantic AI
    ↓
OpenAI / Gemini / DeepSeek / ...
    ↓
Langfuse trace
```

不过这个可以在 Agent 真正开始接入时再部署。

### 6. Apache ECharts

[apache/echarts](https://github.com/apache/echarts?utm_source=chatgpt.com)

这基本不用犹豫。

RiskTrace 需要大量专业研究图：

```text
事件热度 ───────────
情绪指数 ──────╮
新闻量   ──╮   │
股价     ──────╯

          time →
```

还有：

* multi-axis timeline
* heatmap
* scatter
* area
* matrix
* sankey
* graph
* calendar

ECharts 6.1 目前仍然活跃维护。([GitHub][9])

普通金融/研究可视化统一 ECharts。

### 7. React Flow / xyflow

[xyflow/xyflow](https://github.com/xyflow/xyflow?utm_source=chatgpt.com)

这个专门负责 RiskTrace 最特殊的图：

```text
               原油供应中断
                     │
                  供给下降
                     │
              ┌──── 石油 ────┐
              ↓              ↓
           炼化成本          油价
              ↓              ↓
           航空公司        石油公司
```

也就是：

```text
Event
 ↓
Mechanism
 ↓
Industry
 ↓
Company
```

React Flow 就是专门做 interactive node-based UI 的。([GitHub][10])

ECharts 不要承担这个工作。

所以界面分工非常明确：

```text
时间序列 / 矩阵 / 指标
        ↓
     ECharts

传导网络 / Evidence Graph
        ↓
    React Flow
```

### 8. AKShare

[akfamily/akshare](https://github.com/akfamily/akshare?utm_source=chatgpt.com)

MVP 市场数据层可以直接用它。

它覆盖股票、期货、基金、指数、债券、外汇等数据，非常适合先跑历史事件回放。([GitHub][11])

例如：

```text
Event timestamp
       ↓
AKShare
       ↓
000001.SZ
行业指数
上证指数
商品价格
       ↓
统一 MarketObservation
```

但这里必须留一个边界：

AKShare 自己明确说明数据主要面向学术研究，而且部分数据接口可能因外部因素被移除。([GitHub][11])

所以：

> 黑客松/MVP：AKShare。
>
> 真正商业部署：换授权行情源。

Adapter 层正好就是为了以后换这个。

### 9. Celery

[celery/celery](https://github.com/celery/celery?utm_source=chatgpt.com)

下面这些绝对不要放 HTTP request 里同步执行：

```text
fetch source
embedding
dedup
clustering
LLM analysis
reanalyze
snapshot
report generation
notification
```

因此需要后台 worker。

Celery + Redis 是最保守也最成熟的组合之一，支持 worker、retry、broker、result backend 等。([GitHub][12])

我也看了 Prefect，它对数据 pipeline 的 retries、schedule、cache、flow 可视化很好。([GitHub][13])

但当前 RiskTrace：

> **Celery 足够，Prefect 暂时不引入。**

否则又多一个 orchestrator。

---

### 10. Apprise

[caronc/apprise](https://github.com/caronc/apprise?utm_source=chatgpt.com)

Alert Engine 后面可以直接接这个。

它把大量通知渠道统一成一套接口，包括邮件和多种 webhook/消息渠道。([GitHub][14])

这样 RiskTrace 内部只定义：

```text
Alert
 ↓
NotificationService
 ↓
Apprise
 ↓
Email / Webhook / ...
```

不需要每一个通知渠道自己重写。

另外还有一个项目我认为**非常值得研究，但是不能 fork 来改**：

[OpenCTI-Platform/opencti](https://github.com/OpenCTI-Platform/opencti?utm_source=chatgpt.com)

它虽然是网络威胁情报平台，但是它的产品思想和 RiskTrace 惊人地接近：

```text
原始信息
 ↓
实体
 ↓
关系
 ↓
来源
 ↓
confidence
 ↓
analyst review
 ↓
knowledge graph
```

OpenCTI 本身就强调把每条情报关联到 primary source，并管理关系、置信度、first/last seen、connector 和 analyst workflow。([GitHub][15])

RiskTrace 完全可以借鉴它的：

* Evidence 模型
* Source provenance
* Entity relationship
* analyst review
* connector architecture
* graph drill-down

但**只学架构和交互，不拿它代码作为 RiskTrace 底座**。

```text
                    RiskTrace
                        │
        ┌───────────────┴───────────────┐
        │                               │
 React/Vite/shadcn                  FastAPI
        │                               │
 ┌──────┴──────┐                 ┌──────┴─────┐
 │             │                 │            │
ECharts    React Flow        PostgreSQL     Celery
                               │              │
                            pgvector        Redis
                               │
                     Sentence Transformers

                         FastAPI
                            │
                       Pydantic AI
                            │
                      LLM Provider
                            │
                        Langfuse

数据：
AKShare + 合规新闻/RSS/API Adapter

通知：
Apprise
```

我认为这套已经足够固定下来。**不需要 Milvus、不需要 Kafka、不需要 Kubernetes、不需要 LangGraph、不需要 Prefect，也暂时不需要 FinGPT。**
