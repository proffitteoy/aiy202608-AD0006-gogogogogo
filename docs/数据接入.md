对，这个判断更准确。你这三个 Demo 不应该被“整理成系统内部特殊格式后手工喂进去”，而应该把问题拆成两个系统组件：

1. 一套统一的“信息源接入接口”
2. 一套只负责 Demo 的“历史流回放处理器”

核心原则是：Demo 数据和真实数据在进入主 Pipeline 之后必须完全一致，不能给 Demo 写第二套分析逻辑。

架构应该变成：

```text
                  ┌─ Real Source Adapter
真实新闻/API ─────┤
                  │
                  │        Unified Ingestion API
                  ├───────────────┐
                  │               ↓
Demo Dataset ─ Demo Replay ─→ Source/Event Stream
                                  ↓
                           Rule Algorithm 1
                           事件归类 / 聚类
                                  ↓
                           Rule Algorithm 2
                           Admission / 入库
                                  ↓
                           Rule Algorithm 3
                           Admission Score
                                  ↓
                           Rule Algorithm 4
                           Posterior Calibration
                                  ↓
                        Agent 1 Opinion Extractor
                                  ↓
                        Agent 2 Report Generator
```

这里最重要的是：

```text
真实数据和 Demo 数据只允许在“数据从哪里来”这一步不同。
```

进入 `Unified Ingestion API` 后，系统不应该知道它到底来自微博、新闻 API，还是 Demo Replay。

你这三个 Word 文件本质上就是三个“历史事件数据集”，不是三个特殊 Demo。

---

第一套需要设计的是 `Source Ingestion API`。

比如统一成：

```http
POST /api/v1/ingestion/items
```

输入：

```json
{
  "external_id": "deepseek-stcn-20250211",
  "source": {
    "provider": "stcn",
    "type": "news",
    "level": "professional_media"
  },

  "published_at": "2025-02-11T13:33:00+08:00",
  "collected_at": "2025-02-11T13:35:12+08:00",

  "title": "DeepSeek之后，金融大模型将迎哪些变化？",

  "content": "...",

  "url": "...",

  "metadata": {
    "author": "何柳颖"
  }
}
```

这里暂时甚至不应该有：

```json
{
  "event_id": "...",
  "sentiment": "...",
  "risk": "...",
  "topic": "..."
}
```

因为这些应该由你的规则算法和 Agent 后续产生。

也就是说接入层只回答一个问题：

> “我现在收到了一条什么信息？”

不回答：

> “这条信息属于哪个金融事件？”

后者是系统核心能力。

---

第二套才是 Demo 的关键：`Demo Replay Processor`。

它不是简单地：

```python
for article in articles:
    send(article)
```

而应该有一个虚拟时钟 `VirtualClock`。

例如 DeepSeek 数据真实时间顺序是：

```text
2025-01-20  DeepSeek R1 发布
      ↓
2025-01-27  市场关注概念股
      ↓
2025-02-11  银行/券商部署
      ↓
2025-02-14  分析师失业讨论
      ↓
2025-08-04  银行落地效果降温
```

Demo 时不用真的等半年。

可以映射成：

```text
真实时间                     Demo 时间

2025-01-20 10:00      →     00:00
2025-01-27 07:47      →     00:15
2025-02-11 13:33      →     00:30
2025-02-14 09:18      →     00:45
2025-08-04 11:24      →     01:00
```

于是现场 1 分钟就能跑完一个半年事件。

数学上就是做一个时间映射：

[
\tau_i
======

\alpha (t_i-t_0)
]

其中：

* (t_i)：真实发布时间
* (t_0)：事件起点
* (\tau_i)：Demo 中的虚拟时间
* (\alpha)：时间压缩系数

实际工程里甚至可以不用严格线性映射，我更建议采用“序列保持 + 可控间隔”：

[
t_i<t_j
\Rightarrow
\tau_i<\tau_j
]

只要求保持偏序，不要求保持真实时间间隔。

因为半年压缩以后，真实时间差本身已经没有展示意义。

---

所以 Demo Processor 至少需要这些状态：

```text
STOPPED
RUNNING
PAUSED
COMPLETED
```

以及：

```text
start()
pause()
resume()
reset()
seek()
set_speed()
```

API 可以设计为：

```http
POST /api/v1/demo/{demo_id}/start
POST /api/v1/demo/{demo_id}/pause
POST /api/v1/demo/{demo_id}/resume
POST /api/v1/demo/{demo_id}/reset

POST /api/v1/demo/{demo_id}/speed
```

例如：

```json
{
  "speed": 20
}
```

或者更适合现场：

```json
{
  "mode": "fixed_interval",
  "interval_ms": 5000
}
```

即每 5 秒扔一条消息进去。

我更推荐后者。

因为 Demo 最重要的是可控，而不是真实。

---

三个 Demo 数据最终也不需要什么复杂 Ground Truth 目录。

可以直接做：

```text
demo/
├── deepseek-r1/
│   ├── manifest.json
│   └── records.jsonl
│
├── energy-transition/
│   ├── manifest.json
│   └── records.jsonl
│
└── real-estate-policy/
    ├── manifest.json
    └── records.jsonl
```

`manifest.json`：

```json
{
  "id": "deepseek-r1",
  "name": "DeepSeek R1 金融市场影响",
  "description": "DeepSeek R1 发布后金融行业舆论与市场影响",

  "replay": {
    "mode": "fixed_interval",
    "interval_ms": 5000
  },

  "start_at": "2025-01-20T00:00:00+08:00"
}
```

`records.jsonl` 就全部是：

```json
{"published_at":"2025-01-20T10:00:00+08:00","source":...}
{"published_at":"2025-01-27T07:47:00+08:00","source":...}
{"published_at":"2025-02-11T13:33:00+08:00","source":...}
```

Replay Processor 做：

```text
读取
 ↓
按 published_at 排序
 ↓
VirtualClock
 ↓
逐条释放
 ↓
POST /ingestion/items
```

这样它甚至不需要知道 RiskTrace 后面是什么。

---

还有一个细节我认为非常重要：必须区分来源时间、采集时间、服务端接收时间和回放时间。

```json
{
  "published_at": "2025-02-11T13:33:00+08:00",
  "collected_at": "2026-08-04T00:00:00+08:00",
  "replay_at": "2026-08-05T11:42:03+08:00"
}
```

`received_at` 不由客户端传入，而由 ingestion 服务在真正收到请求时生成并在响应中返回：

```json
{
  "received_at": "2026-08-05T11:42:03.021+08:00"
}
```

四个时间语义分别是：

```text
published_at
原事件什么时候发生

collected_at
来源资料什么时候被采集；只有日期精度时必须保留精度元数据

received_at
RiskTrace 什么时候真正收到数据

replay_at
Demo 虚拟流什么时候把它释放出来
```

主算法判断事件时间演化时应该主要使用：

[
published_at
]

而不是：

[
received_at
]

否则回放 2025 年事件时，系统会认为所有新闻都是 2026 年 8 月突然发生的。

---

再往前走一步，你其实可以把这个组件抽象成：

```text
StreamProvider
```

实现两个 Provider：

```text
LiveStreamProvider
DemoReplayProvider
```

两者最终都输出：

```text
SourceRecord
```

那么整个系统就是：

```text
             StreamProvider
                   │
       ┌───────────┴───────────┐
       ↓                       ↓
LiveStreamProvider      DemoReplayProvider
       │                       │
       └───────────┬───────────┘
                   ↓
               Ingestion
                   ↓
             RiskTrace Core
```

这比给 Demo 单独开“Demo 模式分析算法”干净得多。

而且以后你真接：

```text
财联社
雪球
微博
RSS
爬虫
Webhook
```

只是增加新的：

```text
StreamProvider / SourceAdapter
```

RiskTrace Core 一行不用改。

你现在这三个文件真正需要做的工作，因此不是继续人工整理内容，而是：

```text
Word 原始资料
     ↓
一次性转换脚本
     ↓
标准 SourceRecord JSONL
     ↓
DemoReplayProvider
     ↓
统一 Ingestion API
     ↓
现有四层规则 + 两个 Agent
```

这才应该成为现在 Demo 系统的实现方式。

## 2026-08-05 Demo 来源侧实现状态

当前 `demo/src/risktrace_demo` 已实现本文定义的来源侧边界：

- 三份 DOCX 通过一次性转换器生成统一 `SourceRecord` JSONL，不预填事件、情绪、主题或风险字段；
- `DemoReplayProvider` 支持 `STOPPED / RUNNING / PAUSED / COMPLETED / DEGRADED`，以及
  `start / pause / resume / stop / reset / seek / set_speed`；
- 成功投递后才推进 checkpoint；2xx 响应中的 `outcome=duplicate` 被视为幂等成功，HTTP 409
  表示同一来源身份的不可变内容冲突并停止回放；连续失败显式进入 `DEGRADED`；
- `published_at` 保留历史主时间轴，`collected_at` 保留汇编采集日期，`replay_at` 记录回放释放
  时间；`received_at` 由 ingestion 服务在接收时生成，Demo 客户端不得传入；
- 三个场景共解析 24 条候选记录，其中 22 条可转换，2 条因完全缺失发布时间进入
  `rejected.jsonl`；所有场景均明确标记行情不可用、互动量不可用和舆情样本稀疏；
- 原资料没有随附许可凭证，当前 `license_scope` 为 `unknown_internal_demo_only`，不能据此认定
  原文允许二次分发。

当前后端 `SourceRecord` schema 和 ingestion service 已出现在工作树中，但 FastAPI 尚未挂载统一
ingestion 路由。因此代码状态是“DOCX 转换、回放状态机、HTTP 发送端与 schema 契约已实现”，
不是“API、数据库、事件引擎端到端已验证”。后端路由落地后，必须复用同一 schema，不能为 Demo
新增专用分析路径。
